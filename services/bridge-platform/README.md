# Bridge platform service

This module owns Bridge app membership, the shop catalog, device plugin grants, Axiom balances, weekly work leases, legal acceptance and app moderation. It does not replace the existing Red-XAI account service or its MFA/session checks.

## Integration tools under review

`canonical-auth-broker.cjs` is an unwired client for the primary website's observed password/MFA/me flow. It uses a fresh isolated transient cookie jar, exact subject/device/nonce binding, authoritative matching AMR, and a completion timestamp from its own successful transaction. Its receipt is not an owner grant or central-readiness proof. Real disposable-account verification, scoped upstream session cleanup, central revocation, app membership, moderation and deletion contracts remain unresolved. It never automatically logs out the primary account because the existing logout route's scope is unverified.

[SANDBOX-E2E.md](SANDBOX-E2E.md) documents the resumable real-provider billing harness and protected credentials. The harness uses fixture identity and storage, requires actual signed Stripe delivery and a human Sandbox Checkout, and cannot establish production account readiness. No real-provider success is inferred from its mocked guard tests.

[RETENTION.md](RETENTION.md) documents timestamped IP/ended-ban/Bridge-deletion metadata and the dry-run planner's opt-in, revision-bound cleanup. The owner approved the refund windows and retention periods on November 2, 2026, recorded in `app/legal-content.cjs` as scoped policy decisions. Those decisions produce a draft engine policy, not an executable cleanup approval. Untimestamped legacy records stay retained. The full agreements remain draft; operator/address details are unset and production cleanup, external logs, support and backup lifecycle still require implementation and verification.

## Production integration

Instantiate `RedXStore` with a provisioned scoped server-only account database credential. It uses `redxai_accounts` and a separate `rxa-bridge-platform.red-xai.db` record through the dedicated native `record-cas` API. The separate RedX source candidate implements that API with an exact table lookup, native whole-record comparison/commit and synchronous durability; its deployment and namespace provisioning remain unverified. Query-layer `{Tx[]}`/`{Require[]}` alone do not isolate other REST writers or guarantee native crash atomicity. The Bridge adapter has no BoxQL fallback and rejects an older server's unknown-route 404. It never overwrites a canonical account/password/MFA record. `MemoryStore` is for tests; `FileStore` requires explicit development mode. `createPlatform({production:true})` refuses either development store.

The authenticated endpoint is `/v1/db/{database}/record-cas/{encodeURIComponent(fullRecordPath)}`, where `fullRecordPath` is the complete `.red-xai.db:Record[ID=...]` path. Every capable response carries `X-Redx-Record-CAS: 1`. GET returns `{record:{key,revision,payload}}`, where `payload` is the opaque JSON state string; only a marked 404 with `code: "record_not_found"` means an absent record. POST accepts `{expected_revision,record:{key,revision,payload}}`; zero expects absence, each next revision is exactly one greater, and the key is immutable. Success must be status 200 with `{ok:true,revision,seq}` and a positive safe-integer durable sequence. A stale revision or initial insert race returns 409. Async durability, unsupported backends, malformed acknowledgements and unavailable routes fail closed. The existing fresh authority evidence, namespace/write/conflict probes and release readiness checks are still required before production use.

Pass a private Ed25519 signing key and an independent random 32-byte-or-longer IP-HMAC key from protected server configuration. Do not ship them to Electron or put them in plugin manifests. Configure `ownerSubjects` with verified canonical subject IDs in the existing production realm. Ownership requires both that configuration and a fresh authoritative owner/MFA result from `resolvePrivileges`; a username, email match, JSON flag or public Quick Login profile cannot establish ownership. The production website realm is not automatically interchangeable with the separate `red-xai-accounts` OIDC realm.

`createNativeAuthenticator` verifies Quick Login `bridge.app` tokens at the existing live userinfo endpoint, or manual `X-RedX-Session` credentials at the existing account `me` endpoint. It accepts `trustedIP(req)` only from a correctly configured reverse proxy. Do not trust arbitrary forwarded-IP headers. `resolvePrivileges` is a server adapter, not a request-body decoder; it must prove MFA/authentication time and any owner or recovery permission through the actual identity authority. Missing proof leaves those capabilities disabled.

Create the HTTP handler with `createHandler({platform,authenticate,verifyCSRF,extraRoutes,rawWebhook})`. The default URL prefix is `/redxai-bridge/api`. Keep the process bound to loopback behind the existing HTTPS proxy, preserve original `Host: red-xai.com`, and preserve the existing site's unrelated routing. Browser writes require the configured same-origin CSRF verifier. Native calls use bearer/session headers and device signatures. Wrong Host and cross-origin calls are refused.

Every device is enrolled with an Ed25519 public key and a single-use challenge. The private device key belongs in OS-protected encrypted credential storage. Protected requests send:

* `X-Bridge-Device`: SHA-256 of the normalized public SPKI PEM.
* `X-Bridge-Time`: current Unix milliseconds.
* `X-Bridge-Nonce`: at least 20 random base64url characters.
* `X-Bridge-Signature`: Ed25519 signature, base64url encoded, over `METHOD + '\n' + pathAndQuery + '\n' + SHA256(rawBody) + '\n' + timeMs + '\n' + nonce`.

The verifier enforces a bounded clock window and persistent replay nonces. A plugin token is also signed and bound to the canonical account and device key. Obtaining a license for another device requires a separate grant or a verified recovery. Before executing a paid plugin, obtain/validate a current online license; an old signed token alone is insufficient to ignore a refund or recovery revocation. This is cryptographic key binding, not a claim of tamperproof hardware attestation.

## Work leases and weekly quotas

The configured six paid tiers plus Free reset at Monday 00:00 UTC. `/usage/start` reserves at most 15 seconds of the remaining active-work budget before a task runs. The client must heartbeat every 10 seconds; each accepted heartbeat settles elapsed time, refunds unused reservation and reserves the next bounded window. `/usage/stop` settles the final actual elapsed interval and releases the unused remainder. Idle time after stop is not charged. One account can hold one active metering session, so overlapping local tasks must share that session and charge the union of active time once. Crawler pages are debited separately before fetching.

The gateway/process manager must refuse a task without a valid lease and cancel/restrict background execution when the lease expires, connectivity is lost, a ban is returned, or a quota is exhausted. Ruby has unlimited active minutes, but still needs authenticated leases and retains crawler/concurrency safety limits. A modified local desktop cannot be made tamperproof by a server heartbeat; no remote hardware-attestation claim is made.

## Payments and Axioms

Root's Stripe integration owns Checkout, Billing, raw webhook signature verification and account configuration. Do not expose `applyPayment`, `syncSubscription` or `applyRefund` as client-callable HTTP operations. The success page does not fulfill purchases. The verified provider adapter obtains the authoritative order with `getOrder(orderId)` and calls:

```js
await platform.applyPayment({verified:true,paid:true,eventId,checkoutSessionId,
  orderId,sub,deviceId,amountCents,currency:'usd',subscriptionId,periodEndMs});
await platform.syncSubscription({verified:true,eventId,sub,subscriptionId,
  status,tier,periodEndMs});
await platform.applyRefund({verified:true,eventId,checkoutSessionId,totalRefundedCents});
```

`totalRefundedCents` is cumulative per original Checkout payment; out-of-order and duplicate refund events cannot double-debit. Axiom amounts are integer hundredths, with $1 = 1 AX and a minimum purchase of $5.01. They cannot be transferred or cashed out. Credits retain funding lots. A refund removes unspent AX; spent refunded allocations become debt and affected plugins are suspended until that debt is repaid. Full direct plugin refunds revoke its allocations. Financial history stays in the audited ledger after active entitlements expire or are removed.

Before creating a new paid Checkout session, call `authorizePurchase(actor)` to recheck current legal/device/ban state and block owner charges, then require the order subject/device to match the caller. Use the order ID as the provider Checkout idempotency key. `withBillingState(fn)` offers a serialized, guarded transaction for provider customer/session mappings; the callback must be side-effect-free because a storage conflict can retry it. Never perform an external charge inside that callback. `RedXStore` accepts a separate `recordKey` if provider mappings need another record.

Owner benefits are verified server-side: all catalog plugins and all tier benefits free, unlimited enrolled devices, no expiry. They do not mint an infinite AX balance and cannot create Checkout orders. Admins receive no owner purchase benefits.

## Moderation, identity and legal boundaries

Owner-only plugin publishing accepts deterministic allowlisted recipe actions, not executable uploaded code. Only owner/MFA sessions can upload a raster image or edit products. Images are limited to 5 MiB and bounded PNG/JPEG/WebP dimensions/container metadata; active SVG/HTML uploads are refused. The media server must send the returned MIME type, `X-Content-Type-Options: nosniff`, a restrictive CSP and immutable content-hash URLs.

Admins can moderate regular Bridge members, gift/remove entitlements and AX, and search app membership. They cannot target the owner or other admins, grant admin, publish plugins or configure Stripe. IPs are stored as keyed hashes. An authorized exact IP search can match associated hashes, but responses show only counts; raw historical IPs are not disclosed. Shared-IP bans are refused if they would indirectly ban a protected owner/admin.

Global ban/unban and global deletion must delegate to `authority.moderate` / `authority.deleteAccount` using the user's actual central authority and required MFA. The platform validates moderation actions and expiry before making an upstream call, generates its own request ID and requires a typed completion receipt through `authority-confirmation.cjs`. A resolved promise, `undefined`, `{ok:false}`, inherited claims, mismatched subject/request IDs or incomplete effect acknowledgements do not permit local completion writes. These receipts define an internal trusted-adapter contract; they are not claimed primary HTTP response shapes or proof that those routes have been deployed.

Each newer completion receipt needs own data fields `{verified:true,completed:true,sub,action,scope,requestId}` matching the server-issued operation. For global ban, bind `sub` to the affected canonical target, `action:'ban'`, `scope:'global'`, exact `untilMs`, `banned:true` and `sessionsRevoked:true`; global unban uses `action:'unban'`, `untilMs:0` and `banned:false`. Global deletion binds the actor's subject, `action:'delete'`, `scope:'global'`, `accountDeleted:true` and `sessionsRevoked:true`. Reset calls `authority.revokeBridgeSession(actor,{allDevices:false,clientId:'bridge',appNumber:6,deviceId,requestId})` and requires `action:'revoke'`, `scope:'bridge'`, matching device/client/app/allDevices fields and `sessionsRevoked:true`; it leaves canonical Saved Apps membership intact. No receipt may explicitly claim `ok:false` or `success:false`. The trusted adapter must authorize, perform and independently verify the actual effect before returning a receipt; do not create it from request-body claims. Cross-service partial failures still require reconciliation in the actual adapter.

Bridge-only deletion calls `authority.deleteBridgeMembership(actor,{clientId:'bridge',appNumber:6,requestId})` with a fresh platform-issued operation ID. This trusted adapter must remove only Bridge from the actor's canonical Saved Apps record and revoke that actor's Bridge sessions/grants across devices. It must preserve other apps, the central account and global finance, and independently verify the current result before returning own data fields `{verified:true,completed:true,requestId,sub:actor.sub,scope:'bridge',clientId:'bridge',appNumber:6,membershipRemoved:true,sessionsRevoked:true}` without an explicit failure or global-account-deletion claim. Client-supplied request IDs and legacy-shaped receipts cannot authorize a new deletion. New memberships have a server generation that rotates on verified rejoin; the final local commit checks that it still matches the generation captured before the authority call. A prior or delayed receipt cannot delete a newer membership. Each invocation gets a fresh ID; an adapter must independently reconcile a retry's actual effect rather than return an old receipt. Previously stored confirmed-deletion metadata remains readable for scoped retention, which does not permit reusing it as a new operation response. If the adapter is absent, deletion fails before session-revoke calls or local writes. An unconfirmed or mismatched response cannot mark local membership deleted. The production factory requires this adapter; `readiness().bridgeDeletion` and `/me.capabilities.bridgeDeletion` report callback availability, while deployment readiness separately requires verified operational evidence.

After confirmed Bridge-only deletion, local Bridge profile/device/legal/session state clears while global AX, subscriptions, purchases, financial history, quota and recovery history remain. Hashed security associations remain subject to their scoped retention and ban/hold protections. A minimal Bridge-only deletion receipt permits later allowlisted profile cleanup; a global or unconfirmed deletion record cannot. `/account/join` requires authoritative `freshLoginVerified` proof to rejoin deleted membership, and never resets weekly quota or recovery history. Global deletion also cancels active provider subscriptions before the central account is removed; global deletion requires the explicit `DELETE RED-XAI ACCOUNT` confirmation and the authoritative service's password/MFA checks. Removing a live paid subscription requires `authority.cancelSubscription` to cancel real recurring provider billing before clearing the active entitlement; removing a gift does not cancel unrelated billing.

Both paid-subscription removal and global deletion require an exact internal cancellation receipt `{verified:true,completed:true,ok:true,scope:'bridge',action:'cancel-subscription',sub,subscriptionId,requestId,status:'canceled'}` from `authority.cancelSubscription(actor,{sub,subscriptionId,requestId})`. The platform generates the request ID, binds the exact target/provider subscription, and rejects undefined, false, mismatched or merely scheduled-period-end results. The billing adapter may return this receipt only after current provider identity/mode/customer/canceled-state verification and successful durable entitlement synchronization. No direct local removal or deletion follows an unconfirmed result. A newly added uncanceled recurring plan also blocks completion. Global deletion with paid plans requires recent authoritative reauthentication before any pre-cancellation; an unverified password string alone cannot trigger billing changes. Actual multi-service partial failures still require reconciliation: confirmed cancellation of one plan cannot be undone by locally restoring grants if a later independent operation fails.

Supply exactly three versioned legal documents through `legalDocuments` before legal acceptance is available. The client must implement actual scroll-to-bottom and separate Read/Agree checkboxes, then use `/legal/read` and the single-use `/legal/accept` grant. The service records version/device/time; it cannot prove a human actually read prose. Reset revokes the current Bridge session and clears that device's acceptance, requiring sign-in and acceptance again. Draft policies require legal review before making business or recovery guarantees.

## Release readiness

`GET /redxai-bridge/api/readiness` is public and GET-only. It returns only fixed app/issuer, billing mode, agreement version, `ready` and allowlisted capability booleans. Host/origin checks still apply. Probes are bounded, coalesced and briefly cached; missing, failed or timed-out evidence returns false. Timed-out underlying provider work keeps its single-flight slot until it actually settles, so repeated public calls cannot accumulate provider batches. An authenticated Quick Login profile does not prove owner/MFA readiness.

The protected authority module must implement `verifyDeploymentReadiness({issuer,clientId,appNumber,ownerSubjects,legalVersion,signal})` as read-only verification of the actual deployed authority and completed integration evidence. Its result must be `{verified:true,issuer:'https://red-xai.com',clientId:'bridge',appNumber:6,checkedAtMs,canonicalAccounts:true,mfa:true,reauthentication:true,sessionRevocation:true,moderation:true,recovery:true,freshLogin:true,bridgeMembershipDeletion:true,globalAccountDeletion:true,owners:[{sub,verified:true,mfaRequired:true}],deviceProof:true,legalAcceptance:true,legalVersion,usageEnforcement:true,persistence:{namespace:'bridge-platform-v1',durableWrite:true,casConflict:true}}`. Evidence older than ten minutes is refused. Every configured owner needs an exact canonical binding and required MFA. Persistence evidence must concern completed durable-write and conflicting-revision checks in this scoped namespace; the route also performs a current RedX read and refuses empty/uninitialized or development stores. Do not implement this adapter as hardcoded true values, derive it from client claims, or run destructive account probes from the public GET. Unverified native account contracts remain unavailable.

Legal readiness requires the source documents to have `requiresReview:false`, status `approved` or `published`, and complete public `businessDetails`: `legalName`, `supportContact`, `privacyContact`, `refundPolicy`, `cancellationPolicy`, `jurisdiction`, `retentionPeriods`, `subprocessors`, `internationalTransfers`, `rightsProcess`. An explicit source `review` and protected server `legalApproval` must each contain `{approved:true,businessDetailsReviewed:true,version,reviewedAtMs,contentSha256}`; `contentSha256` is produced by `readiness.contentHash(legal)` and binds the version, documents and business details. `legalApproved:true` alone is insufficient. The local release guard refuses unreviewed/draft or changed text before contacting production. The existing draft is deliberately unchanged and cannot pass.

Billing readiness revalidates all eight provider prices/products and the explicit restricted portal. Configure `stripeWebhookEndpointId` in protected server configuration. Its current Stripe endpoint must be enabled, match mode, use the fixed `/redxai-bridge/api/stripe/webhook` HTTPS URL and pinned SDK API version, and subscribe to every handled event. The service also needs a valid signed delivery receipt bound to this endpoint ID, mode and signing-secret fingerprint; rotation invalidates that evidence until another delivery succeeds. The probe reads that receipt without writing platform state. This proves delivery only: actual Sandbox paid Checkout → signed webhook → grant → refund/cancellation/renewal verification remains separate required deployment evidence. A Sandbox service can never report overall live readiness.

The Stripe adapter's mocked regression checks also cover raw signature rejection, mode and account/device/amount binding, Checkout idempotency, paid-only async fulfillment, cumulative refunds, provider subscription cancellation and ordinary dispute holds. A lost dispute does not become won merely because an incoming event payload says so: the adapter retrieves the provider's current object. Full subscription reversals cancel future recurring billing before acknowledgement. No test here makes a live API call or proves sandbox configuration.

`radar.early_fraud_warning.created` requires a current provider lookup and known paid order/receipt bindings before the internal `recordFraudWarning({verified:true,eventId,warningId,chargeId,paymentIntentId,orderIds,actionable,createdAtMs,billingFence?})` method records it. This is a manual review queue: it cannot refund, debit, grant, revoke or otherwise change money or entitlements. A warning's charge/PaymentIntent/order/source-time binding is immutable. Identical current outcomes do not add duplicate audit entries or state writes; a freshly retrieved retry may update the same warning's observed `actionable` snapshot without changing its binding. Only warning-created events are subscribed here, so the flag is not promised to update automatically after a later refund or dispute. `actionable:false` does not acknowledge or resolve pending manual review. The bounded queue refuses a new warning after 1,000 records rather than silently dropping pending evidence; an actual protected review/resolution workflow is still required.

`/admin/fraud-warnings` requires the configured verified owner, recent authoritative MFA, device proof and current legal acceptance. Administrators and regular users cannot read it. It returns `{warnings:[{warningId,chargeId,paymentIntentId,orderIds,actionable,createdAtMs,firstSeenMs,lastSeenMs}],page,totalPages,total,pageSize:10}` with `query.page` or native POST `body.page`. It exposes no raw provider object, profile, email or payment credentials and provides no refund or resolution mutation route. Pending warnings protect their associated retention evidence; financial records, provider bindings and the audit chain are not purged by the retention planner.

Renewal handling retrieves the current invoice and paginated paid InvoicePayments, validates the account, currency, mode, monthly catalog price, service period and current PaymentIntent, then records an immutable receipt. The initial invoice reuses its Checkout purchase instead of recording a second sale. A reversal arriving before `invoice.paid` discovers these provider allocations first. Shared PaymentIntent reversals allocate cumulative cents proportionally to each receipt, capped by its paid amount; fractional residual cents stay unallocated until a later cumulative reversal. Unknown or incomplete bindings retry with an error. The supported native subscription configuration is one monthly catalog item, quantity one, with no proration or extra invoice lines. Keep portal plan changes, coupons, taxes and extra invoice items disabled until their invoice accounting is implemented and tested; cancellation/payment-method management is supported.

Dispute reconciliation always retrieves the current provider object. Open disputes hold the affected balance/licenses; lost disputes reverse the paid allocation. Pending appeals keep an existing loss reversed. A genuine provider win, prevention or closed warning reinstates only the dispute-loss component, while actual cash refunds remain cumulative. AX reinstatement repays debt before restoring spendable funds, licenses retain device-recovery revocations, and subscription wins restore only an unexpired purchased period without restarting canceled recurring billing. Webhook processing uses a durable five-minute lease and transaction fencing: an expired worker cannot overwrite a newer reconciliation. Retry identity includes the current provider result, so a retried older notification can still reconcile a newer provider state. Regression tests cover these paths with injected provider objects and no real charges. Provider contracts: [Dispute](https://docs.stripe.com/api/disputes/object), [InvoicePayment](https://docs.stripe.com/api/invoice-payment/object), [paginated InvoicePayments](https://docs.stripe.com/api/invoice-payment/list), and the official [Node resource](https://github.com/stripe/stripe-node/blob/master/src/resources/InvoicePayments.ts).

Before live rollout, verify the real production owner/MFA adapter, actual central moderation/deletion routes, account app-membership projection, RedX dialect/permissions and revision-conflict behavior against the deployed server. Also verify webhook fulfillment/refunds in an isolated Stripe environment, reverse-proxy Host/CSRF behavior, device recovery identity checks and actual gateway lease termination on all three desktop platforms. `platform.readiness()` exposes missing central capabilities; do not replace missing authority with a permissive mock.
